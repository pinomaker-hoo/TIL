## 1. 왜 메시지 큐를 쓰는가

### Q1. 메시지 큐의 도입 이유를 설명하라.

| 목적 | 설명 |
| --- | --- |
| **비동기 처리** | 사용자가 기다릴 필요 없는 작업(메일, 푸시, 썸네일 생성)을 응답에서 분리해 API 지연을 줄인다 |
| **결합도 분리** | 생산자는 소비자가 누구인지, 살아있는지 몰라도 된다. 소비자 추가가 생산자 배포 없이 가능하다 |
| **부하 평준화 (Load Leveling)** | 순간 트래픽 폭증을 큐가 흡수해 뒤쪽 시스템은 자기 속도로 처리한다 |
| **장애 격리** | 소비자가 죽어도 메시지는 큐에 남아 있다가 복구 후 처리된다 |
| **재처리** | (스트리밍) 오프셋을 되돌려 과거 데이터를 다시 흘려보낼 수 있다 |

### Q2. 메시지 큐를 쓰면 무엇이 나빠지는가? (반드시 함께 답할 것)

1. **최종 일관성**: 처리 완료 시점을 보장할 수 없다 → "결제는 됐는데 포인트가 아직 안 붙었다"
2. **중복 처리**: at-least-once가 기본이라 소비자가 멱등해야 한다
3. **순서 문제**: 전역 순서는 보장되지 않는다
4. **디버깅 난이도**: 흐름이 끊겨서 추적이 어렵다 → Trace ID 전파 필수
5. **운영 대상 증가**: 브로커 자체가 죽으면 전체가 멈춘다. 모니터링·알람·용량 관리가 필요하다

> 답변 포인트: "동기로 충분한 것을 굳이 큐로 넘기면 복잡도만 늘어납니다. **사용자가 결과를 즉시 기다려야 하는가**를 기준으로 판단합니다."

## 2. 메시지 큐 vs 이벤트 스트리밍

| | 메시지 큐 (RabbitMQ, SQS) | 이벤트 스트리밍 (Kafka, Kinesis) |
| --- | --- | --- |
| 모델 | **소비하면 사라진다** (destructive read) | **로그에 남는다**, 소비자가 오프셋을 관리 |
| 재처리 | 불가 (한 번 ack하면 끝) | **오프셋을 되돌려 재처리 가능** |
| 다중 소비자 | 경쟁 소비(Competing Consumer)로 나눠 처리 | 컨슈머 그룹별로 **같은 데이터를 각각 전부** 소비 |
| 라우팅 | Exchange/바인딩으로 유연한 라우팅 | 토픽/파티션 단위, 단순 |
| 처리량 | 수만 msg/s | **수십만~수백만 msg/s** |
| 보존 | 소비 전까지 (짧음) | 기간/용량 기준 (며칠~영구) |
| 적합 | 작업 분배, RPC, 지연 큐, 복잡한 라우팅 | 로그·이벤트 소싱·CDC·스트림 처리·분석 |

**한 줄 정리**: "RabbitMQ는 **일을 나눠주는 큐**, Kafka는 **다시 읽을 수 있는 로그**다."

## 3. Kafka 핵심

### Q1. Kafka의 구조를 설명하라.

```
Producer ──(key로 파티션 결정)──→ Topic
                                   ├─ Partition 0 : [0][1][2][3][4] ...  ← append-only 로그
                                   ├─ Partition 1 : [0][1][2] ...
                                   └─ Partition 2 : [0][1][2][3] ...
                                          │
              Consumer Group A            │            Consumer Group B
              (C1: P0, C2: P1,P2)  ───────┴──────→     (C1: P0,P1,P2)
              → 파티션을 나눠 가짐               → 같은 데이터를 독립적으로 전부 소비
```

- **파티션**: 병렬 처리의 단위. 각 파티션 안에서만 순서가 보장된다.
- **오프셋**: 파티션 내 메시지의 위치 번호. **소비자가 어디까지 읽었는지를 스스로 커밋**한다.
- **컨슈머 그룹**: `group.id`가 같으면 파티션을 나눠 갖는다. **한 파티션은 그룹 내 한 소비자에게만 할당**된다.

### Q2. 컨슈머 수를 파티션 수보다 늘리면?

**남는 소비자는 아무 파티션도 할당받지 못하고 논다.** 즉 **파티션 수 = 컨슈머 병렬도의 상한**이다.

- 그래서 처리량이 부족하면 먼저 파티션 수를 늘려야 한다.
- 단, **파티션은 늘릴 수만 있고 줄일 수 없다.** 또 늘리면 **키 → 파티션 매핑이 바뀌어 기존 순서 보장이 깨진다.**
- 파티션이 너무 많으면 브로커의 파일 핸들/메모리, 리더 선출 시간, 리밸런싱 비용이 커진다.

### Q3. 리밸런싱(Rebalancing)이란? 왜 문제가 되는가?

컨슈머가 추가/제거되거나 죽었다고 판단될 때 파티션을 다시 배분하는 과정이다.

- **문제**: 기본(Eager) 방식은 리밸런싱 동안 **그룹 전체가 소비를 멈춘다(Stop-The-World).**
- 흔한 원인: `max.poll.interval.ms` 안에 처리를 못 끝내서 브로커가 죽은 걸로 판단 → 리밸런싱 → 더 느려짐 → 무한 반복(**리밸런싱 스톰**)
- 대응
  - `max.poll.records`를 줄여 한 번에 가져오는 양을 줄인다
  - 무거운 처리는 별도 스레드/워커로 넘기고 poll 루프는 가볍게 유지
  - **Cooperative Sticky 리밸런싱**(점진적 재배분) 사용
  - `session.timeout.ms` / `heartbeat.interval.ms` 조정, **정적 멤버십(`group.instance.id`)** 으로 재배포 시 불필요한 리밸런싱 방지

### Q4. `acks` 설정과 ISR

```
acks=0   : 보내고 확인 안 함        → 가장 빠름, 유실 가능
acks=1   : 리더가 받으면 성공        → 리더가 복제 전에 죽으면 유실
acks=all : ISR 전부가 받으면 성공    → 가장 안전, 느림
```

- **ISR(In-Sync Replicas)**: 리더를 충분히 따라잡은 복제본 집합.
- `acks=all` + `min.insync.replicas=2` (+ replication factor 3) 조합이 **유실 방지의 표준 설정**이다. ISR이 2개 미만이면 쓰기를 거부해서, "복제본 없이 리더에만 쓰고 죽는" 상황을 막는다.
- `enable.idempotence=true`(프로듀서 멱등성)로 재시도 시 중복 적재를 막을 수 있다.

### Q5. Kafka는 왜 빠른가?

1. **순차 디스크 I/O**: append-only 로그라 랜덤 I/O가 없다. 순차 쓰기는 디스크에서도 매우 빠르다.
2. **페이지 캐시 활용**: JVM 힙이 아니라 OS 페이지 캐시를 캐시로 쓴다.
3. **Zero-copy(sendfile)**: 디스크 → 네트워크로 커널 영역에서 바로 전송, 유저 공간 복사 생략.
4. **배치 + 압축**: 메시지를 모아 한 번에 전송(`linger.ms`, `batch.size`), snappy/lz4/zstd 압축.
5. **파티션 기반 수평 확장**.

### Q6. 리텐션과 로그 압축(Log Compaction)의 차이

- **Retention (`delete`)**: 기간(`retention.ms`)이나 크기 기준으로 오래된 세그먼트를 삭제한다.
- **Compaction (`compact`)**: **키별 최신 값만 남기고** 이전 값들을 정리한다. → "현재 상태" 스냅샷 용도(예: 사용자 프로필 최신값, CDC 테이블 미러링)로 쓴다.

**공부할 것**: 참고 [Kafka](../messageQueue/kafka.md), [Kinesis](../messageQueue/kinesis.md)

## 4. RabbitMQ 핵심

### Q1. Exchange 타입 4가지

```
Producer → Exchange ──(binding key 규칙)──→ Queue → Consumer
```

| 타입 | 라우팅 방식 | 용도 |
| --- | --- | --- |
| **Direct** | routing key 완전 일치 | 특정 큐로 정확히 전달 |
| **Fanout** | 바인딩된 모든 큐에 복제 | 브로드캐스트 |
| **Topic** | 와일드카드 패턴 (`order.*.created`) | 유연한 구독 |
| **Headers** | 헤더 값 매칭 | 드물게 사용 |

### Q2. ack와 prefetch

- **수동 ack(`manual ack`)**: 처리 완료 후 ack를 보내야 큐에서 제거된다. **처리 전에 ack하면(auto ack) 소비자가 죽었을 때 메시지가 유실된다.**
- **prefetch(QoS)**: 소비자가 ack 없이 미리 받아둘 메시지 수. 너무 크면 한 소비자가 메시지를 독점해 **부하 분산이 깨지고** 메모리를 먹는다. 처리 시간이 긴 작업은 보통 **1~10**으로 작게 잡는다.
- **DLX(Dead Letter Exchange)**: reject/nack되거나 TTL이 만료된 메시지를 보내는 곳. **지연 큐(delayed queue)** 도 TTL + DLX 조합으로 구현한다.

**공부할 것**: 참고 [RabbitMQ](../messageQueue/rabbitmq.md), [ActiveMQ](../messageQueue/activemq.md)

## 5. 전달 보장과 커밋 시점

### Q1. 왜 대부분 at-least-once인가?

**처리와 오프셋 커밋(또는 ack)이 원자적이지 않기 때문**이다.

```typescript
// 처리 후 커밋 → at-least-once (중복 가능, 유실 없음) ✅ 일반적 선택
await process(message);
await consumer.commitOffsets();   // 여기서 죽으면 → 다음에 같은 메시지 재소비 (중복)

// 커밋 후 처리 → at-most-once (유실 가능)
await consumer.commitOffsets();
await process(message);           // 여기서 죽으면 → 그 메시지는 영영 처리 안 됨 (유실)
```

**중복은 멱등성으로 해결할 수 있지만 유실은 복구할 수 없다.** 그래서 표준은 **처리 후 커밋 + 멱등 소비자**다.

### Q2. 그럼 exactly-once는?

- Kafka의 트랜잭션(`transactional.id` + read-process-write)은 **Kafka → Kafka 구간에서만** exactly-once를 보장한다.
- 소비 결과를 **외부 DB나 외부 API에 쓰는 순간 그 보장은 깨진다.**
- 현실적인 답: **at-least-once 전달 + 소비자 멱등 처리 = 결과적으로 exactly-once (effectively-once)**

### Q3. 멱등 소비자 구현

```typescript
// 처리 이력 테이블(Inbox) — 비즈니스 로직과 같은 트랜잭션에 묶는다
await dataSource.transaction(async (manager) => {
  try {
    await manager.insert(ProcessedEvent, { eventId: msg.id });  // UNIQUE 제약
  } catch (e) {
    if (isDuplicateKey(e)) return;      // 이미 처리됨 → 무시
    throw e;
  }
  await handleBusinessLogic(manager, msg);
});
```

- 대안: **상태 전이 조건부 UPDATE** (`WHERE status = 'PENDING'`), **자연 키 UNIQUE 제약**(주문번호 + 결제ID).
- 이벤트에는 **고유 ID, 발생 시각, 스키마 버전**을 항상 포함시킨다.
- 이력 테이블은 **주기적으로 오래된 행을 정리**해야 무한정 커지지 않는다.

## 6. 순서 보장

### Q1. 메시지 순서는 어떻게 보장하는가?

- Kafka: **파티션 내부에서만 보장.** 순서가 중요한 단위(`orderId`, `userId`)를 **메시지 키**로 지정하면 같은 키는 항상 같은 파티션으로 간다.
- RabbitMQ: **큐 하나 + 소비자 하나**일 때만 보장. 소비자를 늘리면 깨진다.
- SQS: 표준 큐는 순서 미보장. **FIFO 큐**는 `MessageGroupId` 단위로 보장(대신 처리량 제한).

### Q2. 순서 보장의 대가는?

- 순서를 지키려면 **같은 키를 하나의 소비자가 직렬로 처리**해야 하므로 **병렬도가 그 키에 묶인다.**
- 키가 편중되면 **핫 파티션**이 생겨 특정 소비자만 밀린다.
- 파티션 수를 늘리면 **키 매핑이 바뀌어 기존 순서 가정이 깨진다.**

### Q3. 그래서 실무에서는?

**순서에 의존하지 않는 설계가 더 안전하다.**

- 이벤트에 **버전/시퀀스 번호**를 담고, 소비자는 **자기가 가진 버전보다 낮으면 무시**한다.
- 상태 전이를 조건부로 만든다 (`WHERE status = 'PENDING'`) → 순서가 뒤집혀도 잘못된 전이가 일어나지 않는다.
- "이벤트에 최종 상태 전체를 담기(state-carried event)"도 순서 의존을 줄이는 방법이다.

## 7. 실패 처리 - 재시도와 DLQ

### Q1. 소비 실패 시 처리 흐름

```
소비 실패
  ├─ 일시적 오류(네트워크, 5xx, 락 경합) → 재시도 (지수 백오프 + Jitter)
  │     └─ N회 초과 → DLQ 이동 → 알람 → 원인 분석 → 수동/배치 재처리
  └─ 영구적 오류(스키마 불일치, 존재하지 않는 데이터) → 즉시 DLQ (재시도 무의미)
```

**핵심 포인트: 오류를 재시도 가능/불가능으로 구분하는 것**이 설계의 시작이다.

### Q2. 왜 무한 재시도를 하면 안 되는가?

- Kafka에서는 실패한 메시지 하나가 **파티션 전체의 진행을 막는다** (head-of-line blocking). 이걸 **독성 메시지(poison message)** 라고 한다.
- 재시도가 부하를 증폭시켜 **이미 죽어가는 하위 시스템을 확실히 죽인다** (retry storm).
- 그래서 **재시도 횟수 상한 + 백오프 + DLQ**가 세트다.

### Q3. 재시도를 어디에 두는가?

| 방식 | 설명 | 주의 |
| --- | --- | --- |
| 인메모리 재시도 | 소비자 안에서 즉시 몇 번 재시도 | 길어지면 `max.poll.interval` 초과 → 리밸런싱 |
| **재시도 토픽/큐** | `retry-5s`, `retry-1m` 같은 별도 토픽으로 넘김 | 메인 파티션을 막지 않음 (권장) |
| 지연 큐 | RabbitMQ TTL+DLX, SQS `DelaySeconds`, BullMQ `backoff` | 지연 시간 제어 용이 |

### Q4. DLQ 운영에서 흔한 실수

- **DLQ를 만들어놓고 아무도 안 본다.** → DLQ 메시지 수에 **반드시 알람**을 건다.
- 재처리 도구가 없다. → 관리자 화면이나 재처리 스크립트를 미리 만들어둔다.
- DLQ로 보낼 때 **원본 메시지 + 실패 사유 + 스택 트레이스 + 시도 횟수**를 같이 저장해야 분석할 수 있다.

## 8. 컨슈머 랙과 처리량 튜닝

### Q1. 컨슈머 랙(Consumer Lag)이란?

**Lag = (파티션의 최신 오프셋) - (컨슈머가 커밋한 오프셋)** = 아직 처리하지 못한 메시지 수.

- **MQ 모니터링의 1순위 지표.** 랙이 계속 증가하면 소비 속도 < 생산 속도라는 뜻이다.
- 확인: `kafka-consumer-groups.sh --describe`, Burrow, Prometheus JMX Exporter / SQS는 `ApproximateNumberOfMessagesVisible`, `ApproximateAgeOfOldestMessage`.

### Q2. 랙이 쌓이면 어떻게 대응하는가?

```
1. 원인 파악 : 생산량 급증인가, 소비 처리 시간 증가인가, 특정 파티션만인가(핫 키)
2. 소비자 확장 : 컨슈머 인스턴스 추가 (단, 파티션 수가 상한)
3. 파티션 증설 : 병렬도 상한 자체를 올림 (순서/키 매핑 영향 주의)
4. 처리 최적화 : 건별 처리 → 배치 처리, N+1 제거, 외부 호출 병렬화·타임아웃
5. 분리        : 무거운 작업을 별도 토픽/워커로 떼어냄, 우선순위 분리
```

### Q3. 배치 처리와 백프레셔

- 건별 DB 쓰기를 **벌크 insert/upsert**로 바꾸면 처리량이 수 배 오른다. 대신 **배치 중 일부 실패 시 처리 방식**(전체 실패 vs 개별 격리)을 정해야 한다.
- **백프레셔**: 소비자가 감당 못할 때 `pause()`로 poll을 멈추거나 prefetch를 낮춰 유입을 조절한다. 무작정 받아서 메모리에 쌓으면 OOM으로 죽는다.

## 9. DB와의 정합성

### Q1. "DB 저장 + 메시지 발행"을 어떻게 원자적으로 하는가?

**Outbox 패턴**. 이벤트를 같은 DB의 outbox 테이블에 **같은 트랜잭션으로** 저장하고, 별도 릴레이 워커나 **CDC(Debezium)** 가 읽어서 발행한다.

> 코드 예제와 상세 설명은 [MSA 문서 - Outbox 패턴](./msa.md#q3-outbox-패턴이란) 참고.

핵심만 반복하면:
- 발행 후 상태 갱신 전에 죽으면 **중복 발행**이 가능하다 → 소비자 멱등성이 전제.
- 반대 방향은 **Inbox 패턴**(수신 메시지 ID 저장으로 중복 처리 차단).

### Q2. 트랜잭션 커밋 전에 이벤트를 쏘면 왜 안 되는가?

소비자가 너무 빨라서 **아직 커밋되지 않은 데이터를 조회하러 오면 "없음"으로 처리**된다. (경합 조건)

- ORM/프레임워크의 **커밋 이후 훅**(`AFTER_COMMIT` 이벤트)을 쓰거나 Outbox로 해결한다.
- 그래도 프로세스가 커밋 직후 죽으면 유실되므로, 정합성이 중요한 도메인은 Outbox가 정답이다.

## 10. 기술 선택 비교표

| | Kafka | RabbitMQ | AWS SQS | Redis Stream | BullMQ |
| --- | --- | --- | --- | --- | --- |
| 모델 | 로그 스트리밍 | 메시지 브로커 | 관리형 큐 | 로그 스트리밍(경량) | 작업 큐(Redis 기반) |
| 처리량 | 매우 높음 | 높음 | 높음 | 높음 | 중간 |
| 재처리 | O (오프셋 이동) | X | X | O | 제한적 |
| 순서 | 파티션 단위 | 큐+단일 소비자 | FIFO 큐만 | 스트림 단위 | 큐 단위 |
| 지연/스케줄 작업 | 약함 | TTL+DLX | DelaySeconds(최대 15분) | 약함 | **강함(cron, delay)** |
| 운영 부담 | 높음 | 중간 | **없음(관리형)** | 낮음(Redis 있으면) | 낮음 |
| 적합 | 이벤트 소싱, CDC, 로그, 분석 | 복잡한 라우팅, RPC, 작업 분배 | AWS 환경 비동기 처리 | 이미 Redis 쓰는 중소 규모 | Node.js 백그라운드 작업 |

**선택 기준 답변 예시**

> "우선 **관리형(SQS)** 으로 시작할 수 있으면 그렇게 합니다. 운영 비용이 0에 가깝기 때문입니다. **재처리·이벤트 소싱·다중 소비자**가 필요하면 Kafka, **복잡한 라우팅이나 지연 큐**가 필요하면 RabbitMQ, 이미 Redis를 쓰고 있고 Node.js 백그라운드 작업(재시도·스케줄·동시성 제어)이 목적이면 BullMQ를 씁니다."

**공부할 것**: 참고 [Message Queue 선택 가이드](../messageQueue/index.md), [BullMQ](../messageQueue/bullmq.md) / [BullMQ(NestJS)](../bull/bullmq.md), [SQS](../messageQueue/amazon-sqs.md), [NATS](../messageQueue/nats.md), [Redis Pub/Sub](../messageQueue/redis-pubsub.md)

## 11. 운영 장애 사례

면접에서 "겪은 문제"를 물으면 이 목록에서 고르면 된다.

| 사례 | 원인 | 대응 |
| --- | --- | --- |
| 리밸런싱 무한 반복 | 처리 시간이 `max.poll.interval.ms` 초과 | poll 크기 축소, 처리 분리, Cooperative Sticky |
| 특정 파티션만 랙 폭증 | 키 편중(핫 파티션) | 키 설계 변경, 서브키 추가, 파티션 재설계 |
| 메시지 유실 | `acks=1`에서 리더 장애 / auto-ack | `acks=all` + `min.insync.replicas=2` / manual ack |
| 중복 결제 | 재시도 + 멱등성 없음 | Idempotency-Key, 처리 이력 테이블 |
| 독성 메시지로 소비 중단 | 무한 재시도 | 재시도 상한 + DLQ |
| 브로커 디스크 풀 | 리텐션 설정 미비, 소비 정체 | retention 조정, 압축, 랙 알람 |
| 배포 중 메시지 유실 | Graceful shutdown 미구현 | SIGTERM 시 처리 중 메시지 완료 후 종료 |
| 큐는 비었는데 처리 안 됨 | 소비자가 죽었는데 알람 없음 | 컨슈머 하트비트/랙 기반 알람 |

## 12. 실무 경험 질문

- 메시지 큐를 어떤 문제 때문에 도입했는가? 도입 전후 무엇이 달라졌는가? (수치)
- 메시지가 중복 처리된 적이 있는가? 어떻게 발견하고 막았는가?
- 메시지 유실을 겪은 적이 있는가? 원인은?
- 컨슈머 랙이 쌓였을 때 어떻게 진단하고 해결했는가?
- 실패한 메시지는 어떻게 처리하는가? DLQ 재처리 절차가 있는가?
- 파티션 수(또는 워커 동시성)를 어떤 근거로 정했는가?
- 메시지 스키마를 변경해야 할 때 어떻게 배포했는가?
  → **하위 호환 유지 → 필드 추가만 → 소비자 전부 이전 후 제거**, 스키마 레지스트리 활용
- 브로커가 죽으면 서비스는 어떻게 동작하는가? (생산 실패 시 폴백 — 로컬 저장 후 재발행 / 동기 폴백 / 사용자 오류 반환)

## 13. 학습 체크리스트

**Level 1 — 말할 수 있어야 함**

- [ ] 메시지 큐 도입 이유 5가지와 대가 5가지를 말할 수 있다
- [ ] 메시지 큐와 이벤트 스트리밍의 차이를 설명할 수 있다
- [ ] Kafka의 토픽/파티션/오프셋/컨슈머 그룹 관계를 그릴 수 있다
- [ ] 파티션 수와 컨슈머 수의 관계를 설명할 수 있다
- [ ] at-least-once가 기본인 이유를 커밋 시점으로 설명할 수 있다
- [ ] exactly-once가 왜 어려운지 설명할 수 있다
- [ ] `acks`와 `min.insync.replicas` 조합의 의미를 설명할 수 있다

**Level 2 — 직접 해봐야 함**

- [ ] 로컬(Docker)로 Kafka를 띄우고 프로듀서/컨슈머를 만들어봤다
- [ ] 컨슈머를 늘리고 줄이며 **리밸런싱이 일어나는 것**을 관찰했다
- [ ] 소비 중 강제 종료시켜 **중복 소비**를 재현해봤다
- [ ] 멱등 소비자(처리 이력 테이블)를 구현해 중복을 막아봤다
- [ ] 지수 백오프 재시도 + DLQ를 구성해봤다
- [ ] `kafka-consumer-groups.sh --describe`로 랙을 확인해봤다
- [ ] Outbox 테이블 + 릴레이 워커를 만들어봤다

**Level 3 — 설계할 수 있어야 함**

- [ ] 주어진 요구사항에서 큐 기술을 선택하고 근거를 댈 수 있다
- [ ] 토픽/파티션/키 설계를 순서·병렬도 관점에서 할 수 있다
- [ ] 실패 처리 정책(재시도 대상 구분, 횟수, 백오프, DLQ, 알람)을 설계할 수 있다
- [ ] 브로커 장애 시 서비스 동작(폴백)을 설계할 수 있다
