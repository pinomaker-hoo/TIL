## 1. Redis란 무엇이고 왜 빠른가

### Q1. Redis는 무엇인가?

**인메모리 키-값 저장소**다. 단순 캐시를 넘어 다양한 자료구조를 제공해서 캐시, 세션 저장소, 랭킹, 큐, 분산 락, 레이트 리미터, Pub/Sub 등으로 쓴다.

### Q2. 왜 빠른가? (단골)

**"메모리라서 빠르다"만 말하면 부족하다.** 4가지로 답한다.

1. **인메모리**: 디스크 I/O가 없다. 마이크로초 단위 응답.
2. **싱글 스레드 이벤트 루프**: 명령을 하나씩 순차 처리하므로 **락과 컨텍스트 스위칭 비용이 없다.** 동시성 제어가 필요 없어 오버헤드가 사라진다.
3. **I/O 멀티플렉싱**: epoll/kqueue로 하나의 스레드가 수만 개의 커넥션을 처리한다.
4. **효율적인 자료구조 구현**: 작은 데이터는 ziplist/listpack 같은 압축 인코딩으로 저장하고 커지면 자동 전환한다. SDS, skiplist 등 목적에 맞게 최적화되어 있다.

> 보충: Redis 6부터 **네트워크 I/O(읽기/쓰기)는 멀티스레드**로 처리할 수 있다(`io-threads`). 다만 **명령 실행 자체는 여전히 단일 스레드**다. 이 구분을 정확히 말하면 좋다.

### Q3. Memcached와 비교하면?

| | Redis / Valkey | Memcached |
| --- | --- | --- |
| 자료구조 | String, List, Hash, Set, ZSet, Stream 등 | String만 |
| 영속성 | RDB/AOF 지원 | 없음 |
| 복제/HA | Replication, Sentinel, Cluster | 없음(클라이언트 샤딩) |
| 스레드 | 명령 실행 단일 스레드 | 멀티스레드 |
| 적합 | 대부분의 경우 | **단순 문자열 캐시 + 멀티코어 활용 극대화** |

## 2. Valkey - 왜 생겼고 무엇이 다른가

### Q1. Valkey가 무엇인가?

2024년 3월 Redis Inc.가 Redis의 라이선스를 오픈소스 라이선스(BSD)에서 **RSALv2 / SSPL 듀얼 라이선스로 변경**하면서, 이를 그대로 쓸 수 없게 된 클라우드 사업자와 커뮤니티가 **Redis 7.2.4를 포크해 Linux Foundation 산하에서 만든 오픈소스 프로젝트**가 Valkey다. AWS, Google, Oracle, Ericsson 등이 참여했다.

- 이후 Redis는 2025년 5월 Redis 8부터 **AGPLv3를 추가**해 다시 오픈소스 라이선스 선택지를 제공했다.
- AWS ElastiCache / MemoryDB, Google Memorystore 등 주요 관리형 서비스가 Valkey 옵션을 제공하며, **같은 스펙에서 Redis보다 저렴하게 책정**된 경우가 많다.

### Q2. Redis와 Valkey의 차이는?

- **프로토콜(RESP)과 명령어는 호환된다.** 기존 클라이언트 라이브러리와 애플리케이션 코드를 거의 그대로 쓸 수 있다.
- 포크 이후 각자 발전하면서 차이가 생기고 있다.
  - **Valkey**: 멀티코어 활용(비동기 I/O 스레딩) 강화, 키를 슬롯별 사전으로 분리해 **메모리 효율과 클러스터 확장성 개선**, 키당 오버헤드 축소 등 **성능·효율 중심**의 개선이 이어졌다.
  - **Redis**: 벡터 검색, JSON, 시계열 등 **모듈 기능이 코어에 통합**되는 방향.
- 결론적으로 **캐시/세션/락 같은 일반 용도라면 사실상 대체 가능**하고, Redis Stack의 특정 모듈 기능(RediSearch, RedisJSON 등)에 의존하면 이전이 간단하지 않다.

### Q3. 그래서 무엇을 선택하는가? (답변 예시)

> "표준적인 캐시/세션/큐 용도라면 **라이선스가 명확하고 관리형 비용이 저렴한 Valkey**를 기본 후보로 봅니다. 명령어 호환이라 마이그레이션 비용도 낮습니다. 다만 RediSearch나 RedisJSON 같은 **Redis Stack 모듈에 의존하는 기능이 있으면** 대체 여부를 먼저 검증해야 하고, 팀의 운영 경험과 관리형 서비스 지원 범위도 함께 고려합니다."

> 주의: 버전별 세부 기능은 계속 바뀌므로, 면접에서는 **"라이선스 변경이 배경이고, 프로토콜 호환이며, Valkey는 성능·효율, Redis는 모듈 통합 방향"** 이라는 큰 그림까지만 확실히 말하는 것이 안전하다.

## 3. 자료구조와 실무 활용

| 타입 | 대표 명령 | 실무 활용 |
| --- | --- | --- |
| **String** | `SET/GET/INCR/SETNX` | 캐시, 카운터(조회수), 분산 락, 레이트 리미터 |
| **Hash** | `HSET/HGET/HGETALL` | 객체 저장(사용자 프로필). 필드 단위 수정이 가능해 JSON String보다 유리 |
| **List** | `LPUSH/RPOP/BLPOP` | 간단한 큐/스택, 최근 목록. `BLPOP`으로 블로킹 소비 |
| **Set** | `SADD/SISMEMBER/SINTER` | 중복 제거, 태그, 좋아요 여부, 공통 친구(교집합) |
| **Sorted Set** | `ZADD/ZRANGE/ZRANGEBYSCORE` | **랭킹, 리더보드, 지연 큐, 슬라이딩 윈도우 레이트 리미터** |
| **Stream** | `XADD/XREADGROUP/XACK` | 컨슈머 그룹 기반 이벤트 큐 (Pub/Sub과 달리 **영속 + 재처리**) |
| Bitmap | `SETBIT/BITCOUNT` | 출석 체크, DAU (1억 유저를 12MB로) |
| HyperLogLog | `PFADD/PFCOUNT` | 대용량 **고유 방문자 수 근사치** (오차 0.81%, 12KB 고정) |
| Geo | `GEOADD/GEOSEARCH` | 주변 검색 (내부는 ZSet + geohash) |

### 자주 나오는 활용 질문

**Q. 실시간 랭킹을 어떻게 구현하는가?**
→ Sorted Set. `ZADD leaderboard <score> <userId>`로 저장하고 `ZREVRANGE ... 0 9 WITHSCORES`로 상위 10명, `ZREVRANK`로 내 순위를 O(log N)에 얻는다. DB로는 매번 정렬해야 해서 감당이 안 된다.

**Q. API 레이트 리미터를 만든다면?**
```
[고정 윈도우] INCR key + EXPIRE 60  → 단순하지만 경계에서 2배 통과 문제
[슬라이딩 윈도우 로그] ZSet에 요청 timestamp 저장 → ZREMRANGEBYSCORE로 윈도우 밖 제거 → ZCARD로 개수 확인 (정확, 메모리 사용)
[토큰 버킷] Hash에 토큰 수 + 마지막 갱신 시각 → Lua로 원자적 갱신 (버스트 허용, 실무에서 가장 많이 씀)
```
경쟁 조건을 막으려면 **Lua 스크립트로 원자적으로** 처리해야 한다는 점이 핵심이다.

**Q. 선착순 쿠폰 발급은?**
→ `DECR`로 재고를 원자적으로 줄이고 음수면 실패 처리, 중복 방지는 `SADD`(이미 있으면 0 반환)로 판정한다. 여러 명령이 필요하면 Lua로 묶는다. DB에는 큐를 통해 비동기로 반영한다.

**공부할 것**: 참고 [Redis](../redis/redis.md), [Redis Stream](../redis/redis-stream.md)

## 4. 싱글 스레드의 함정

### Q1. 싱글 스레드라서 생기는 위험은?

**하나의 느린 명령이 서버 전체를 멈춘다.** 그동안 다른 모든 클라이언트의 요청이 대기한다.

**운영에서 절대 쓰면 안 되는 명령**

| 위험 명령 | 이유 | 대안 |
| --- | --- | --- |
| `KEYS *` | O(N) 전체 스캔, 수백만 키면 수 초 블로킹 | **`SCAN`** (커서 기반 점진적 순회) |
| `FLUSHALL` / `FLUSHDB` | 대량 삭제 블로킹 | `ASYNC` 옵션 |
| `DEL bigkey` | 큰 키 삭제 시 블로킹 | **`UNLINK`** (백그라운드 해제) |
| `SMEMBERS` / `HGETALL` / `LRANGE 0 -1` | 큰 컬렉션 전체 반환 | `SSCAN`/`HSCAN`, 범위 지정 |
| `SORT`, 큰 `ZRANGEBYSCORE` | O(N log N) | 범위 축소, 사전 계산 |

### Q2. 빅키(Big Key)와 핫키(Hot Key)

- **빅키**: 하나의 키에 수십만 개 원소나 수 MB 값이 들어간 경우. 조회·삭제·마이그레이션 시 블로킹을 일으키고, 클러스터에서는 **슬롯 불균형**을 만든다.
  - 탐지: `redis-cli --bigkeys`, `MEMORY USAGE key`
  - 대응: 키를 샤딩(`user:1:posts:0`, `:1` …), 값 압축, 자료구조 변경
- **핫키**: 특정 키에 요청이 집중되어 그 키가 있는 샤드만 과부하되는 현상.
  - 대응: **로컬 캐시(다계층 캐싱)**, 키 복제(`hot:key:1~N` 랜덤 분산), 읽기 레플리카 활용

## 5. 영속성 - RDB와 AOF

### Q1. RDB와 AOF의 차이는?

| | RDB (스냅샷) | AOF (Append Only File) |
| --- | --- | --- |
| 방식 | 특정 시점 전체를 바이너리로 덤프 | **모든 쓰기 명령을 순차 기록** |
| 파일 크기 | 작음 | 큼 (rewrite로 압축) |
| 복구 속도 | 빠름 | 느림 (명령 재실행) |
| 유실 범위 | **마지막 스냅샷 이후 전부** | `appendfsync` 설정에 따라 최대 1초 |
| 부하 | fork 시점에 스파이크 | 상시 쓰기 부하 |

### Q2. RDB의 fork가 왜 위험한가? (심화)

RDB 저장 시 자식 프로세스를 **fork**하는데, **Copy-On-Write** 때문에 저장 도중 쓰기가 많으면 **메모리 사용량이 최대 2배까지 늘 수 있다.** 메모리가 부족하면 OOM Killer에 죽거나 스왑이 발생해 지연이 폭증한다.

- 그래서 **메모리를 최대 50~60% 정도만 사용**하도록 여유를 두고, `vm.overcommit_memory=1` 설정을 권장한다.
- 대용량 인스턴스에서 fork 자체가 수백 ms 블로킹을 유발할 수 있다(`latest_fork_usec`로 확인).

### Q3. 실무에서는 어떻게 설정하는가?

- **순수 캐시 용도**: 영속성을 꺼도 된다. 유실돼도 DB에서 다시 채우면 되고, 오히려 부하가 줄어든다. (단, **Cold Start 시 DB로 부하가 몰리는 것**은 고려)
- **데이터 저장 용도(세션, 랭킹)**: **AOF `everysec` + RDB 병행**이 일반적이다. Redis 4+의 **혼합 방식(RDB 스냅샷 + 이후 AOF)** 을 쓰면 복구 속도와 안전성을 모두 얻는다.
- **중요**: Redis는 **비동기 복제**라서 마스터가 ack한 뒤 죽으면 복제본에 없는 데이터가 유실될 수 있다. **"Redis는 절대 유실되지 않는다"고 말하면 안 된다.**

## 6. 만료와 Eviction

### Q1. TTL이 지난 키는 언제 삭제되는가?

| 방식 | 동작 |
| --- | --- |
| **Lazy(수동) 만료** | 키에 접근할 때 만료 여부를 확인하고 삭제 |
| **Active(능동) 만료** | 주기적으로 만료 키 일부를 샘플링해 삭제 |

→ **TTL이 지났다고 즉시 메모리가 반환되지는 않는다.** 그래서 만료된 키가 남아 메모리를 차지할 수 있다.

### Q2. maxmemory에 도달하면? (Eviction 정책)

| 정책 | 동작 |
| --- | --- |
| `noeviction` | **쓰기 명령에 에러 반환** (기본값) — 캐시 용도로 쓰면 장애가 된다 |
| `allkeys-lru` | 전체 키 중 가장 오래 안 쓴 것부터 제거 — **일반 캐시의 표준 선택** |
| `allkeys-lfu` | 전체 키 중 **사용 빈도**가 낮은 것부터 제거 — 인기 키가 뚜렷할 때 유리 |
| `volatile-lru` / `volatile-lfu` / `volatile-ttl` / `volatile-random` | **TTL이 설정된 키만** 대상으로 제거 |
| `allkeys-random` | 무작위 제거 |

**자주 나오는 함정 질문**: "캐시로 쓰는데 `noeviction` + TTL 없는 키"라면 메모리가 차는 순간 **모든 쓰기가 실패한다.** 캐시 용도라면 `allkeys-lru`(또는 lfu) + 모든 키에 TTL이 안전한 조합이다.

> Redis의 LRU/LFU는 **정확한 LRU가 아니라 샘플링 기반 근사**(`maxmemory-samples`)다. 전체를 추적하면 메모리와 비용이 크기 때문이다. 이 점을 알면 가점.

## 7. 아키텍처 - Replication, Sentinel, Cluster

### Q1. 구성 4가지

```
[Standalone]  단일 노드. 죽으면 끝. 개발/소규모.

[Replication] Master(쓰기) ──비동기 복제──→ Replica(읽기)
              읽기 분산 가능. 자동 페일오버 없음 → 수동 승격 필요.

[Sentinel]    Sentinel 3대가 마스터를 감시 → 죽으면 투표로 복제본을 승격 (자동 페일오버)
              데이터는 여전히 한 마스터에 전부 → 쓰기 확장 X, 메모리 한계 그대로.

[Cluster]     데이터를 16384개 해시 슬롯으로 나눠 여러 마스터에 분산 (샤딩)
              각 마스터마다 복제본. 쓰기 확장 O, 메모리 확장 O.
```

### Q2. Cluster의 해시 슬롯과 제약

- 키를 `CRC16(key) mod 16384`로 계산해 슬롯을 정하고, 슬롯을 노드에 배분한다.
- **제약: 여러 키를 다루는 명령(`MGET`, `SINTER`, 트랜잭션, Lua)은 키들이 같은 슬롯에 있어야 한다.**
- 해결: **해시 태그** — 키 이름에 `{}`를 쓰면 중괄호 안의 문자열만으로 슬롯을 계산한다.

```
user:{1000}:profile
user:{1000}:orders    → 둘 다 "1000"으로 슬롯 계산 → 같은 노드 → 멀티키 연산 가능
```

- 남용하면 **한 슬롯에 데이터가 몰려 불균형**이 생기므로 꼭 필요한 범위에만 쓴다.
- 노드 수가 바뀌면 **슬롯 마이그레이션(리샤딩)** 이 필요하고, 그 과정에서 `MOVED` / `ASK` 리다이렉트가 발생한다. 클러스터 지원 클라이언트를 써야 한다.

### Q3. Sentinel과 Cluster 중 무엇을 쓰는가?

- **데이터가 한 노드 메모리에 들어가고 HA만 필요** → Sentinel (또는 관리형 서비스의 자동 페일오버)
- **메모리/쓰기 처리량이 한 노드로 부족** → Cluster
- 실무에서는 대부분 **관리형(ElastiCache, MemoryDB, Memorystore)** 을 쓰고 Multi-AZ 자동 페일오버에 맡긴다. 이때 **페일오버 중 수십 초의 쓰기 실패 구간**이 있다는 점을 애플리케이션이 감안해야 한다.

## 8. 캐시로서의 Redis

> 캐시 전략(Cache Aside / Write Through / Write Behind)과 3대 장애(Stampede / Penetration / Avalanche)는 [DB 면접 문서](./db.md#11-캐시와-db-일관성)와 [캐시 문서](../cache/index.md)에 정리되어 있다. 여기서는 Redis 특유의 포인트만 다룬다.

### Q1. 캐시 키를 어떻게 설계하는가?

```
서비스:도메인:식별자:버전   →  order:detail:12345:v2
```

- **네임스페이스를 콜론으로 구분**해 용도를 알아볼 수 있게 한다.
- 스키마가 바뀌면 **키에 버전을 올려** 한 번에 무효화한다 (전체 삭제보다 안전).
- 키가 길면 메모리를 낭비한다. 수천만 키 규모면 키 길이도 유의미한 비용이다.
- **모든 키에 TTL을 설정한다.** TTL 없는 키가 쌓이면 언젠가 메모리가 찬다.

### Q2. Cache Stampede를 Redis에서 어떻게 막는가?

1. **분산 락**: 첫 요청만 DB를 조회하고 나머지는 짧게 대기 후 캐시를 다시 읽는다.
2. **논리적 만료**: TTL은 길게 두고 값 안에 `expireAt`을 넣어, 만료가 임박하면 **오래된 값을 반환하면서 백그라운드로 갱신**한다 (Stale-While-Revalidate).
3. **TTL Jitter**: `TTL + random(0, TTL*0.1)`로 만료 시점을 분산한다.

## 9. 분산 락

### Q1. Redis로 분산 락을 어떻게 구현하는가?

```bash
# 획득 : NX(없을 때만) + PX(만료시간) — 반드시 하나의 원자적 명령으로
SET lock:order:123 <randomToken> NX PX 3000
```

**반드시 지켜야 할 3가지**

1. **TTL 필수**: 락을 잡은 프로세스가 죽어도 자동 해제되어야 한다. TTL 없는 락은 영구 데드락이 된다.
2. **소유권 토큰**: 값에 **랜덤 토큰**을 넣고, 해제할 때 **내 토큰인지 확인 후 삭제**한다. 안 그러면 내 락이 TTL로 만료된 뒤 남이 잡은 락을 내가 지워버린다.
3. **해제는 원자적으로(Lua)**: `GET` 후 `DEL`은 그 사이에 만료될 수 있어 안전하지 않다.

```lua
-- 해제 스크립트: 토큰이 일치할 때만 삭제
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

### Q2. Redis 분산 락의 한계는? (심화, 좋은 답변 소재)

- **TTL이 만료됐는데 작업은 아직 진행 중**이면 두 프로세스가 동시에 임계 구역에 들어간다. → 작업 시간을 넘는 TTL을 잡거나, **워치독(자동 연장, Redisson)** 을 쓴다.
- **Redlock 논쟁**: 여러 독립 노드 과반에서 락을 얻는 Redlock 알고리즘은 Martin Kleppmann이 **GC pause·클럭 드리프트·네트워크 지연 상황에서 안전하지 않다**고 지적했고, 안전이 정말 중요하면 **펜싱 토큰(단조 증가 번호)** 을 자원 쪽에서 검증해야 한다고 주장했다.
- 실무 결론: **"Redis 락은 효율(중복 작업 방지)에는 훌륭하지만, 정확성이 생명인 자원(돈, 재고)의 최종 방어선으로는 부족하다."** 최종 정합성은 **DB의 유니크 제약이나 조건부 UPDATE**로 한 번 더 보장한다.

```sql
-- 락이 실패해도 여기서 막힌다 (최종 방어선)
UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock > 0;
```

## 10. 원자성 - 트랜잭션, Lua, 파이프라이닝

| | 설명 | 주의 |
| --- | --- | --- |
| **파이프라이닝** | 여러 명령을 한 번에 보내 **RTT를 줄임** | **원자성 아님**. 성능 최적화 수단일 뿐 |
| **트랜잭션 (`MULTI`/`EXEC`)** | 큐에 모았다가 한 번에 순차 실행 | **롤백이 없다.** 중간 명령이 실패해도 나머지는 실행됨 |
| **`WATCH`** | 낙관적 락. 감시 중인 키가 바뀌면 `EXEC`가 실패 | 실패 시 재시도 로직 필요 |
| **Lua 스크립트** | 서버에서 **원자적으로 실행** (실행 중 다른 명령 끼어들지 못함) | 길면 서버 블로킹 → 짧고 빠르게 |

**핵심 답변**: "읽고 판단해서 쓰는(read-modify-write) 로직은 여러 명령으로 나누면 경쟁 조건이 생깁니다. Redis에서 이런 로직의 원자성이 필요하면 **Lua 스크립트**를 씁니다. `MULTI/EXEC`는 롤백이 없어서 조건 분기가 필요한 로직에는 적합하지 않습니다."

## 11. Pub/Sub vs Stream vs List

| | Pub/Sub | Stream | List (`BLPOP`) |
| --- | --- | --- | --- |
| 저장 | **저장 안 함(fire-and-forget)** | 로그로 저장 | 큐에 저장 |
| 구독자 없으면 | **메시지 소멸** | 남아 있음 | 남아 있음 |
| 재처리 | 불가 | **가능(오프셋/ID 기반)** | 불가 |
| 소비자 그룹 | 없음(전원 수신) | **있음(XREADGROUP, 분배)** | 경쟁 소비 |
| ack | 없음 | **있음(XACK, PEL로 미처리 추적)** | 없음 |
| 용도 | 실시간 알림, 캐시 무효화 브로드캐스트 | 경량 이벤트 큐 | 단순 작업 큐 |

**중요 포인트**: **Pub/Sub은 메시지를 보관하지 않는다.** 구독자가 잠깐 재시작 중이면 그 사이 메시지는 사라진다. **"중요한 데이터를 Pub/Sub으로 전달하면 안 된다."** 신뢰성이 필요하면 Stream이나 전용 브로커([MQ 면접 문서](./mq.md))를 쓴다.

**공부할 것**: 참고 [Redis Stream](../redis/redis-stream.md), [Redis Pub/Sub](../messageQueue/redis-pubsub.md)

## 12. 운영 장애 사례

| 사례 | 원인 | 대응 |
| --- | --- | --- |
| 순간 전체 응답 지연 | `KEYS *`, 빅키 조회/삭제 | `SCAN`/`UNLINK`, 빅키 분할, slowlog 모니터링 |
| 쓰기 전부 실패 | `maxmemory` 도달 + `noeviction` | eviction 정책 설정, 모든 키에 TTL, 메모리 알람 |
| 메모리 사용률이 안 줄어듦 | 만료 키 지연 삭제, **메모리 단편화** | `INFO memory`의 `mem_fragmentation_ratio` 확인, activedefrag |
| RDB 저장 중 OOM | fork + Copy-On-Write로 메모리 2배 | 메모리 여유 확보(50~60% 사용), overcommit 설정 |
| 캐시 서버 재시작 후 DB 폭주 | Cold Start | 캐시 워밍업, 점진적 오픈, 서킷 브레이커 |
| 특정 노드만 CPU 100% | 핫키 / 슬롯 불균형 | 로컬 캐시, 키 분산, 리샤딩 |
| 페일오버 중 쓰기 실패 | 마스터 승격 시간 동안 쓰기 불가 | 재시도 + 백오프, 타임아웃 설정, 폴백 경로 |
| 커넥션 고갈 | 커넥션 풀 미사용, 누수 | 풀 사용(ioredis/lettuce), 타임아웃, 모니터링 |

**진단 명령**: `INFO`(memory/stats/replication), `SLOWLOG GET`, `--bigkeys`, `--hotkeys`, `MEMORY DOCTOR`, `LATENCY DOCTOR`, `CLIENT LIST`

## 13. 실무 경험 질문

- Redis를 어떤 용도로 썼는가? 캐시 외에 쓴 사례가 있는가?
- 캐시 적중률(Hit Ratio)을 측정해봤는가? 얼마였고 어떻게 올렸는가?
- 캐시와 DB의 데이터가 어긋난 적이 있는가? 어떻게 해결했는가?
- TTL은 어떤 기준으로 정했는가?
- Redis가 죽으면 서비스는 어떻게 동작하는가? (→ **캐시는 없어도 DB로 동작해야 한다. 세션을 Redis에만 두면 전원 로그아웃된다.**)
- 동시성 문제를 Redis로 해결한 경험이 있는가? 그 방식의 한계는 무엇인가?
- 메모리가 부족해진 적이 있는가? 어떻게 대응했는가?
- Valkey로의 전환을 검토해본 적이 있는가? 판단 기준은?

## 14. 학습 체크리스트

**Level 1 — 말할 수 있어야 함**

- [ ] Redis가 빠른 이유를 4가지로 설명할 수 있다
- [ ] 싱글 스레드의 장점과 위험(블로킹 명령)을 함께 설명할 수 있다
- [ ] 자료구조 6종의 대표 활용 사례를 말할 수 있다
- [ ] RDB와 AOF의 트레이드오프, fork/COW 위험을 설명할 수 있다
- [ ] Eviction 정책 이름과 `noeviction`의 위험을 설명할 수 있다
- [ ] Sentinel과 Cluster의 차이를 설명할 수 있다
- [ ] Valkey가 생긴 배경과 Redis와의 관계를 설명할 수 있다
- [ ] Pub/Sub과 Stream의 차이(보관 여부)를 설명할 수 있다

**Level 2 — 직접 해봐야 함**

- [ ] Sorted Set으로 랭킹 API를 만들어봤다
- [ ] Lua 스크립트로 원자적 레이트 리미터를 구현해봤다
- [ ] `SET NX PX` + 토큰 + Lua 해제로 분산 락을 구현해봤다
- [ ] `SLOWLOG`와 `--bigkeys`로 문제 키를 찾아봤다
- [ ] `maxmemory`를 작게 걸고 eviction이 일어나는 것을 관찰했다
- [ ] Cluster를 띄우고 해시 태그 없이 멀티키 명령이 실패하는 것을 확인했다
- [ ] Redis Stream + 컨슈머 그룹으로 이벤트를 처리해봤다
- [ ] Valkey 컨테이너로 기존 코드가 그대로 동작하는지 확인해봤다

**Level 3 — 설계할 수 있어야 함**

- [ ] 캐시 키 네이밍/TTL/무효화 정책을 설계할 수 있다
- [ ] 선착순·재고 차감을 Redis + DB 조합으로 설계할 수 있다 (락의 한계 포함)
- [ ] Redis 장애 시 폴백 동작을 설계할 수 있다
- [ ] 데이터 성격에 따라 영속성 설정과 구성(Sentinel/Cluster)을 선택할 수 있다
