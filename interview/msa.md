## 1. MSA의 정의와 트레이드오프

### Q1. MSA란 무엇인가? 모놀리식과 비교하라.

| | 모놀리식 | MSA |
| --- | --- | --- |
| 배포 단위 | 하나 | 서비스별 독립 |
| 기술 스택 | 통일 | 서비스별 선택 가능 |
| 데이터 | 단일 DB, ACID 트랜잭션 | **서비스별 DB, 분산 트랜잭션 필요** |
| 확장 | 전체를 함께 스케일 | 병목 서비스만 스케일 |
| 장애 | 한 곳이 죽으면 전체 다운 | 격리 가능 (**단, 설계했을 때만**) |
| 디버깅 | 스택 트레이스 하나 | **여러 서비스를 넘나듦 → 추적 도구 필수** |
| 운영 복잡도 | 낮음 | **매우 높음** (인프라, CI/CD, 모니터링) |

### Q2. 언제 MSA를 도입해야 하는가?

**핵심 답변: 기술적 이유보다 조직적/규모적 이유가 우선이다.**

도입할 만한 신호

- 팀이 커져서 **하나의 배포 파이프라인에 병목**이 생긴다 (배포하려면 여러 팀 조율 필요)
- 도메인별로 **트래픽/확장 요구가 극단적으로 다르다** (결제는 안정성, 조회는 처리량)
- 서비스별로 **다른 기술 스택/릴리즈 주기**가 필요하다

도입하면 안 되는 경우

- 팀이 작다 (인프라 운영 비용이 개발 시간을 먹는다)
- 도메인 경계가 아직 불명확하다 → 잘못 자르면 **되돌리기가 매우 비싸다**
- "요즘 다 MSA라서"

> **정답에 가까운 답변**: "모놀리식으로 시작하되 모듈 경계를 명확히 두는 **모듈러 모놀리스**로 만들고, 경계가 검증되고 조직/트래픽이 그 경계를 요구할 때 떼어냅니다." (Martin Fowler의 *Monolith First*)

<br />

### Q3. MSA를 도입하면 무엇이 어려워지는가? (필수 답변)

1. **트랜잭션**: DB가 나뉘어 ACID를 못 쓴다 → 최종 일관성 + 보상 트랜잭션
2. **조회**: JOIN이 불가능하다 → API 조합, 데이터 복제(CQRS), 조회 전용 모델
3. **장애 전파**: 동기 호출 체인이 길면 하나가 느려질 때 전체가 물린다
4. **디버깅**: 로그가 서비스마다 흩어진다 → 분산 추적 필수
5. **운영**: 서비스 수 × (CI/CD + 모니터링 + 알람 + 배포)
6. **테스트**: 통합 테스트가 어렵다 → 계약 테스트(Contract Test)

## 2. 서비스 분리 기준

### Q1. 서비스를 어떤 기준으로 나누는가?

**기술 계층(Controller/Service/Repository)이 아니라 비즈니스 능력(Business Capability) 단위로 나눈다.**

- **DDD의 Bounded Context**를 경계로 삼는다. 같은 "상품"이라도 주문 컨텍스트의 상품(가격/재고)과 카탈로그 컨텍스트의 상품(설명/이미지)은 다른 모델이다.
- 좋은 경계의 기준
  - **높은 응집도, 낮은 결합도**: 한 기능을 바꿀 때 한 서비스만 배포하면 되는가?
  - **함께 변경되는 것은 함께 둔다** (변경 이유가 같은 것끼리)
  - **데이터 소유권이 명확한가**: 이 데이터를 쓸 수 있는 서비스가 하나인가?
- **Conway's Law**: 시스템 구조는 조직 구조를 닮는다. 팀이 소유할 수 있는 크기여야 한다.

### Q2. 서비스가 다른 서비스의 데이터가 필요하면?

우선순위 순서

1. **경계가 잘못됐는지 먼저 의심한다.** 자주 같이 필요하면 하나였어야 할 수도 있다.
2. **API로 조회**한다 (동기, 최신값 필요할 때)
3. **이벤트로 필요한 데이터만 복제해서 로컬에 보관**한다 (조회 성능/독립성 우선, 최종 일관성 허용)
4. **절대 하지 말 것: 다른 서비스의 DB에 직접 접근** → 분산 모놀리스로 가는 지름길

## 3. 서비스 간 통신

### Q1. 동기 통신과 비동기 통신은 어떻게 선택하는가?

| | 동기 (REST / gRPC) | 비동기 (Kafka / SQS / RabbitMQ) |
| --- | --- | --- |
| 응답 | 즉시 결과 필요 | 결과를 기다리지 않음 |
| 결합도 | 높음 (상대가 살아있어야 함) | 낮음 (브로커가 완충) |
| 장애 전파 | **전파됨** | 격리됨 (큐에 쌓임) |
| 일관성 | 즉시 | 최종 일관성 |
| 디버깅 | 쉬움 | 어려움 (흐름 추적 필요) |
| 예시 | 로그인, 결제 승인, 조회 | 알림 발송, 정산 집계, 검색 색인, 통계 |

**판단 기준: "사용자가 지금 이 결과를 기다려야 하는가?"**

- 기다려야 함 → 동기
- 아니면 → 비동기 (그리고 대부분은 아니어도 된다)

### Q2. REST vs gRPC

| | REST(JSON/HTTP1.1) | gRPC(Protobuf/HTTP2) |
| --- | --- | --- |
| 성능 | 보통 (텍스트 직렬화) | 빠름 (바이너리, 멀티플렉싱) |
| 스키마 | OpenAPI (선택적) | **.proto 필수 → 계약이 강제됨** |
| 스트리밍 | 제한적(SSE/WebSocket) | 양방향 스트리밍 지원 |
| 브라우저 | 네이티브 지원 | gRPC-Web 필요 |
| 적합 | 외부 공개 API, 프론트 연동 | **내부 서비스 간 통신** |

일반적인 구성: **외부(클라이언트) ↔ Gateway는 REST/GraphQL, 내부 서비스 간에는 gRPC 또는 이벤트.**

### Q3. 이벤트 기반 아키텍처에서 오케스트레이션 vs 코레오그래피

```
[코레오그래피 Choreography] — 중앙 조율자 없음, 각자 이벤트를 듣고 반응
  주문생성 ──event──→ 결제서비스 ──event──→ 재고서비스 ──event──→ 배송서비스
  장점: 결합도 최소, 서비스 추가 쉬움
  단점: 전체 흐름을 아무도 모른다 → 디버깅/변경이 어렵다

[오케스트레이션 Orchestration] — 중앙 조율자가 순서대로 지시
              ┌──→ 결제서비스
  Orchestrator├──→ 재고서비스
              └──→ 배송서비스
  장점: 흐름이 한 곳에 명시됨, 보상 처리 쉬움
  단점: 조율자가 SPOF·비대해질 수 있음
```

**기준**: 단계가 3개 이하이고 단순하면 코레오그래피, **단계가 많고 보상 로직이 복잡하면 오케스트레이션.**

**공부할 것**: 참고 [Message Queue](../messageQueue/index.md), [Kafka](../messageQueue/kafka.md), [RabbitMQ](../messageQueue/rabbitmq.md), [SQS](../messageQueue/amazon-sqs.md)

## 4. 분산 트랜잭션 - Saga와 Outbox

### Q1. 서비스마다 DB가 다른데 트랜잭션은 어떻게 보장하는가?

**핵심 답변: ACID를 포기하고 최종 일관성 + 보상 트랜잭션(Saga)으로 간다.**

**2PC(Two-Phase Commit)를 왜 안 쓰는가**도 함께 말한다.

- 코디네이터가 SPOF이고, **준비(prepare) 단계에서 모든 참여자가 락을 잡은 채 대기**해 가용성과 처리량이 크게 떨어진다.
- 참여자가 하나라도 응답하지 않으면 전체가 블로킹된다.
- 대부분의 메시지 브로커/NoSQL이 XA를 지원하지 않는다.

<br />

### Q2. Saga 패턴이란?

로컬 트랜잭션의 연쇄로 비즈니스 트랜잭션을 구성하고, **실패하면 앞 단계를 되돌리는 보상 트랜잭션(Compensating Transaction)을 실행**하는 패턴이다.

```
정상:  주문생성(T1) → 결제승인(T2) → 재고차감(T3) → 배송요청(T4)

T3 실패 시 보상 (역순):
        주문취소(C1) ← 결제취소(C2) ← [실패]
```

**설계 시 반드시 고려할 것**

- **보상은 롤백이 아니다.** 이미 커밋된 것을 "되돌리는 새로운 트랜잭션"이다. (결제 취소는 환불이지 없던 일이 아니다)
- 보상 불가능한 작업(메일 발송, 외부 정산)은 **되도록 마지막 단계에 배치**한다.
- 중간 상태가 외부에 노출된다 → `PENDING`, `CONFIRMED`, `CANCELLED` 같은 **명시적 상태 머신**을 둔다.
- **보상 자체도 실패할 수 있다** → 재시도 + DLQ + 수동 개입 경로(운영 어드민)를 준비한다.

<br />

### Q3. Outbox 패턴이란?

**"DB 커밋과 메시지 발행을 원자적으로 만드는" 패턴**이다. MSA 면접에서 가장 점수가 큰 주제다.

**문제 상황**

```typescript
await db.save(order);        // 성공
await kafka.publish(event);  // 여기서 실패하면? → DB엔 있는데 이벤트가 없다 (유실)

// 순서를 바꾸면?
await kafka.publish(event);  // 성공
await db.save(order);        // 실패 → 없는 주문의 이벤트가 나감 (유령 이벤트)
```

**해결: 이벤트를 같은 DB의 outbox 테이블에 같은 트랜잭션으로 저장하고, 별도 프로세스가 읽어서 발행한다.**

```typescript
// 1. 비즈니스 데이터와 이벤트를 하나의 로컬 트랜잭션으로 저장
await dataSource.transaction(async (manager) => {
  const order = await manager.save(Order, dto);
  await manager.save(OutboxEvent, {
    aggregateType: 'Order',
    aggregateId: order.id,
    eventType: 'ORDER_CREATED',
    payload: JSON.stringify(order),
    status: 'PENDING',
  });
});

// 2. 별도 워커(또는 CDC)가 PENDING을 읽어 발행하고 상태를 갱신
async function relay() {
  const events = await outboxRepo.find({ where: { status: 'PENDING' }, take: 100 });
  for (const e of events) {
    await kafka.publish(e.eventType, e.payload);   // 실패해도 PENDING이라 다음에 재시도
    await outboxRepo.update(e.id, { status: 'SENT', sentAt: new Date() });
  }
}
```

- 발행 후 상태 갱신 전에 죽으면 **중복 발행**이 될 수 있다 → **at-least-once**를 전제로 소비자가 멱등해야 한다.
- 폴링 대신 **CDC(Debezium이 binlog를 읽어 Kafka로 발행)** 를 쓰면 지연과 DB 부하를 줄일 수 있다.
- 반대 방향에는 **Inbox 패턴**(수신한 메시지 ID를 저장해 중복 처리 방지)이 있다.

<br />

### Q4. CQRS는 무엇이고 언제 쓰는가?

Command(쓰기)와 Query(읽기) 모델을 분리하는 패턴이다.

- MSA에서는 **여러 서비스에 흩어진 데이터를 조회해야 할 때** 읽기 전용 뷰를 이벤트로 미리 만들어두는 용도로 자주 쓴다.
- 장점: 읽기/쓰기를 독립적으로 최적화·확장, 복잡한 조회를 조인 없이 처리
- 단점: **최종 일관성**(쓰고 나서 바로 조회하면 없을 수 있다), 동기화 코드와 운영 복잡도 증가
- 남용 금지. **읽기 부하가 압도적으로 크거나 조회 모델이 근본적으로 다를 때만** 쓴다.

## 5. 메시지 신뢰성 - 멱등성과 전달 보장

### Q1. 메시지 전달 보장 3가지

| 방식 | 의미 | 현실 |
| --- | --- | --- |
| At-most-once | 최대 1번, 유실 가능 | 로그/메트릭 등 손실 허용 데이터 |
| **At-least-once** | 최소 1번, **중복 가능** | **대부분의 시스템이 채택** |
| Exactly-once | 정확히 1번 | 분산 환경에서 진짜 보장은 매우 어렵고 비쌈 |

**핵심 답변**: "Exactly-once는 사실상 **at-least-once 전달 + 소비자 멱등 처리**로 구현한다. Kafka의 exactly-once도 Kafka 내부(트랜잭션 + idempotent producer)에서만 성립하고, 외부 DB나 API 호출까지는 보장하지 않는다."

<br />

### Q2. 멱등성은 어떻게 구현하는가?

**멱등성 = 같은 요청을 여러 번 처리해도 결과가 같은 성질.**

```typescript
// 방법 1: 처리 이력 테이블 (Inbox) — 가장 확실
async function handle(event: Event) {
  try {
    await processedRepo.insert({ eventId: event.id });  // UNIQUE 제약
  } catch (e) {
    if (isDuplicateKey(e)) return;   // 이미 처리함 → 조용히 무시
    throw e;
  }
  await doBusinessLogic(event);
}

// 방법 2: 상태 전이 조건부 UPDATE — 자연스러운 멱등
await orderRepo.update(
  { id, status: 'PENDING' },     // PENDING일 때만 바뀜 → 두 번째 호출은 0건
  { status: 'PAID' },
);

// 방법 3: Idempotency-Key (외부 API/결제)
// 클라이언트가 UUID를 헤더로 보내고, 서버는 키별 결과를 저장해 재요청 시 같은 응답 반환
```

- 처리 이력 테이블과 비즈니스 로직을 **같은 트랜잭션**에 두어야 "기록은 됐는데 처리는 안 됨"을 막을 수 있다.
- 이벤트에는 **고유 ID와 발생 시각**을 반드시 포함시킨다.

<br />

### Q3. 메시지 순서 보장은?

- Kafka는 **파티션 단위로만 순서를 보장**한다. → 순서가 중요한 단위(예: `orderId`)를 **파티션 키**로 써서 같은 파티션에 보내야 한다.
- 그 대가로 **키가 편중되면 특정 파티션이 핫스팟**이 된다.
- 그래도 재시도/장애로 순서가 뒤집힐 수 있으므로, 이벤트에 **버전(또는 시퀀스 번호)** 을 담아 **오래된 이벤트는 무시**하도록 설계하는 것이 안전하다.

### Q4. 처리에 실패한 메시지는?

```
소비 실패 → 재시도(지수 백오프 + Jitter) → N회 초과 → DLQ(Dead Letter Queue) 이동
                                                      → 알람 → 원인 분석 → 재처리
```

- **무한 재시도 금지**: 독성 메시지(poison message) 하나가 파티션 전체를 막는다.
- DLQ는 **쌓이는지 반드시 모니터링/알람**을 건다. DLQ만 만들고 안 보는 게 가장 흔한 실수다.

## 6. 장애 대응 패턴

### Q1. 서킷 브레이커란?

호출 실패율이 임계치를 넘으면 **아예 호출을 차단하고 즉시 실패(fail-fast)** 시켜, 응답 없는 서비스를 계속 기다리다 스레드/커넥션이 고갈되는 **연쇄 장애(Cascading Failure)** 를 막는 패턴이다.

```
      실패율 임계 초과
CLOSED ─────────────→ OPEN ──일정 시간 후──→ HALF_OPEN
  ↑ (정상 호출)         (즉시 실패 반환)      (탐색 요청 몇 개만 통과)
  └──────────────────────성공───────────────────┘
                          실패 → 다시 OPEN
```

- OPEN 상태에서는 **폴백(Fallback)** 을 제공한다 — 캐시된 값, 기본값, "잠시 후 다시 시도" 응답.

### Q2. 타임아웃과 재시도의 함정

- **타임아웃 없는 호출이 가장 위험하다.** 응답이 안 오면 커넥션과 스레드가 무한정 묶인다.
- **타임아웃은 호출 체인의 안쪽이 더 짧아야 한다.** (A→B→C 일 때 C의 타임아웃 < B < A)
- **재시도는 부하를 증폭시킨다.** 이미 죽어가는 서비스에 3배 트래픽을 보내면 확실히 죽인다(retry storm).
  - 반드시 **지수 백오프 + Jitter**를 쓰고, **재시도 총량 예산(retry budget)** 을 둔다.
  - **멱등하지 않은 요청은 재시도하면 안 된다.** (중복 결제)

### Q3. 그 외 알아둘 패턴

| 패턴 | 목적 |
| --- | --- |
| **Bulkhead** (격벽) | 리소스 풀을 기능별로 분리해 한 기능의 폭주가 전체를 삼키지 못하게 함 |
| **Rate Limiting** | 유입량 상한 (Token Bucket, Leaky Bucket) |
| **Backpressure** | 소비 속도보다 생산이 빠를 때 상류에 신호를 보내 속도를 늦춤 |
| **Graceful Degradation** | 부가 기능(추천, 배지)을 끄고 핵심 기능(주문)을 살림 |
| **Health Check** | Liveness(살아있나, 죽으면 재시작) / Readiness(트래픽 받을 준비됐나) 구분 |
| **Graceful Shutdown** | SIGTERM 수신 → 새 요청 차단 → 처리 중 요청 완료 → 종료 (무중단 배포의 전제) |

## 7. API Gateway · Service Discovery · BFF

### Q1. API Gateway의 역할은?

클라이언트와 내부 서비스 사이의 단일 진입점.

- 라우팅, 인증/인가, **Rate Limiting**, 로깅/추적 ID 주입, 요청/응답 변환, 캐싱, SSL 종료
- 장점: 횡단 관심사를 한 곳에 모으고, 클라이언트가 내부 구조를 몰라도 된다
- 단점: **SPOF와 병목**이 될 수 있다 → 다중화 필수. 비즈니스 로직을 넣으면 게이트웨이가 비대해진다(안티패턴)

### Q2. BFF(Backend For Frontend)란?

클라이언트 종류(웹/모바일/어드민)마다 전용 백엔드를 두는 패턴. 화면마다 다른 데이터 조합·응답 형태 요구를 각 BFF가 흡수해서, 모바일이 5번 호출할 것을 1번으로 줄인다.

### Q3. Service Discovery는 왜 필요한가?

컨테이너 환경에서는 인스턴스의 **IP가 계속 바뀌고 개수도 변한다.** 하드코딩된 주소로는 호출할 수 없다.

- **클라이언트 사이드**: 호출자가 레지스트리(Eureka, Consul)에서 목록을 받아 직접 로드밸런싱
- **서버 사이드**: 로드밸런서/프록시가 라우팅 (**Kubernetes Service + DNS**가 사실상 표준)
- 서비스 메시(Istio, Linkerd)를 쓰면 discovery, 재시도, 서킷 브레이커, mTLS, 트래픽 분할을 **애플리케이션 코드 밖(사이드카)** 에서 처리할 수 있다.

**공부할 것**: 참고 [Kubernetes](../kubernetes/index.md), [ECS vs EKS](../aws/ecs-vs-eks.md)

## 8. 인증과 인가

### Q1. 서비스가 여러 개인데 인증은 어떻게 처리하는가?

**일반적인 구성**

```
Client ──JWT──→ Gateway (서명 검증 + 만료 확인)
                   │  검증된 사용자 정보를 헤더/컨텍스트로 전달
                   ↓
              내부 서비스들 (서명 재검증 or 게이트웨이 신뢰)
```

- **JWT(무상태)**: 서비스마다 인증 서버를 호출하지 않아도 되어 확장에 유리. 단점은 **즉시 무효화(로그아웃/강제 탈퇴)가 어렵다**.
  - 대응: Access Token은 짧게(15분~1시간) + Refresh Token은 서버에 저장해 회수 가능하게, 블랙리스트를 Redis에 두기.
- **세션(상태)**: 무효화가 쉽지만 세션 저장소(Redis)를 공유해야 한다.
- 내부 서비스 간 인증은 **mTLS** 또는 내부 전용 토큰. **"게이트웨이를 통과했으니 내부는 다 신뢰"는 위험하다** (Zero Trust).

**공부할 것**: 참고 [JWT](../server/jwt.md), [Cookie](../server/cookie.md), OAuth2 / OIDC 플로우

## 9. 관측성 (Observability)

### Q1. 여러 서비스를 거치는 요청을 어떻게 추적하는가?

**분산 추적(Distributed Tracing)** — 요청 진입 시 **Trace ID**를 발급하고 모든 하위 호출(HTTP 헤더, 메시지 헤더)에 전파한다. 각 구간은 **Span**으로 기록된다.

```
Trace ID: abc-123
├─ Span: Gateway            (12ms)
   ├─ Span: OrderService    (340ms)
      ├─ Span: PaymentService  (280ms)  ← 여기가 병목
      └─ Span: DB query        (55ms)
```

- 표준은 **OpenTelemetry**, 백엔드는 Jaeger / Zipkin / Datadog / AWS X-Ray.
- Node.js에서는 `AsyncLocalStorage`로 요청 컨텍스트(Trace ID)를 전파한다.

### Q2. 관측성의 세 기둥

| | 답하는 질문 | 도구 |
| --- | --- | --- |
| **Logs** | 무슨 일이 있었나 | 구조화(JSON) 로그 + Trace ID 포함, ELK/Loki |
| **Metrics** | 얼마나 자주/얼마나 느린가 | Prometheus + Grafana |
| **Traces** | 어디서 느려졌나 | OpenTelemetry + Jaeger |

- **로그에 Trace ID를 반드시 넣는다.** 이게 없으면 MSA 로그는 사실상 못 쓴다.
- 핵심 지표: **RED(Rate, Errors, Duration)**, **USE(Utilization, Saturation, Errors)**, 그리고 **p99 지연**. 평균만 보면 안 된다.
- SLI/SLO/에러 버짓 개념을 알면 가점.

## 10. 배포와 운영

### Q1. 무중단 배포 전략

| 전략 | 방식 | 특징 |
| --- | --- | --- |
| **Rolling** | 인스턴스를 순차 교체 | 기본값, 자원 효율적. **구/신 버전이 공존**하므로 하위 호환 필수 |
| **Blue/Green** | 새 환경 전체를 띄우고 트래픽 전환 | 롤백이 즉시. 자원 2배 |
| **Canary** | 일부 트래픽(1% → 10% → 100%)만 새 버전으로 | 위험 최소화. 지표 기반 자동 롤백 가능 |

### Q2. 배포 중 API를 바꿔야 하면?

**구/신 버전이 동시에 떠 있는 순간이 반드시 존재**하므로, 항상 하위 호환을 유지하며 단계적으로 바꾼다.

```
[확장-축소(Expand-Contract)]
1. 새 필드/새 API를 추가한다 (옛 것 유지, optional)
2. 소비자를 새 것으로 모두 이전한다
3. 옛 필드/API를 제거한다   ← 모든 소비자 이전 확인 후
```

- 이벤트 스키마도 동일하다. **필드 삭제·타입 변경은 파괴적 변경**이다. Avro/Protobuf + **스키마 레지스트리**로 호환성을 강제한다.
- DB 마이그레이션도 같은 원칙 (컬럼 추가 → 양쪽 쓰기 → 백필 → 읽기 전환 → 제거).

## 11. 안티패턴

면접에서 "MSA 하면서 겪은 어려움"을 물으면 이 목록에서 고르면 된다.

| 안티패턴 | 문제 |
| --- | --- |
| **분산 모놀리스** | 배포는 나뉘었는데 서로 동기 호출로 얽혀 있어 **같이 배포해야 하고 같이 죽는다.** MSA의 비용만 내고 장점은 없다. |
| **공유 DB** | 여러 서비스가 같은 테이블을 직접 읽고 쓴다 → 스키마 변경이 불가능해진다 |
| **너무 이른 분리 / 나노서비스** | 경계가 검증되기 전에 잘게 쪼개 통신 오버헤드와 운영 비용만 폭증 |
| **동기 호출 체인** | A→B→C→D. D가 100ms 느려지면 A는 타임아웃. 가용성은 각 서비스 가용성의 **곱**으로 떨어진다 |
| **엔티티 서비스** | `UserService`, `ProductService`처럼 데이터 테이블 단위로 쪼갬 → 하나의 기능에 5개 서비스 호출 필요 |
| **관측성 없는 MSA** | 장애가 나도 어디서 났는지 못 찾는다 |
| **버전 없는 이벤트** | 스키마를 바꾸는 순간 소비자들이 조용히 깨진다 |

## 12. 실무 경험 질문

- MSA 환경에서 **데이터 정합성이 깨진 경험**이 있는가? 어떻게 발견하고 복구했는가?
- 서비스 간 순환 의존이 생긴 적이 있는가? 어떻게 풀었는가?
- 특정 서비스 장애가 전체로 번진 적이 있는가? 이후 무엇을 바꿨는가?
- 모놀리식을 MSA로 분리한다면 **어디서부터** 시작하겠는가?
  → **스트랭글러 픽(Strangler Fig)**: 게이트웨이를 앞에 두고, 경계가 명확하고 변경이 잦거나 트래픽이 큰 도메인부터 하나씩 떼어내 트래픽을 옮긴다.
- 이벤트 스키마를 변경해야 할 때 어떻게 배포했는가?
- 중복 메시지 때문에 문제가 생긴 적이 있는가? 멱등성을 어떻게 확보했는가?
- 서비스 간 통신에서 타임아웃/재시도 값을 어떤 근거로 정했는가?

## 13. 학습 체크리스트

**Level 1 — 말할 수 있어야 함**

- [ ] MSA의 장점과 **대가**를 각각 3개 이상 말할 수 있다
- [ ] 언제 MSA를 도입하면 안 되는지 근거를 댈 수 있다
- [ ] 동기/비동기 통신 선택 기준을 사례로 설명할 수 있다
- [ ] 2PC를 안 쓰는 이유를 설명할 수 있다
- [ ] Saga의 보상 트랜잭션이 롤백과 어떻게 다른지 설명할 수 있다
- [ ] 서킷 브레이커의 3가지 상태 전이를 그릴 수 있다

**Level 2 — 구현해봐야 함**

- [ ] Outbox 테이블 + 릴레이 워커를 직접 만들어봤다
- [ ] 소비자 멱등 처리(처리 이력 테이블 또는 조건부 UPDATE)를 구현해봤다
- [ ] 재시도 + 지수 백오프 + DLQ를 구성해봤다 ([BullMQ](../messageQueue/bullmq.md) / SQS / Kafka)
- [ ] Trace ID를 서비스 간에 전파하고 로그에 남겨봤다
- [ ] Health check와 Graceful Shutdown을 붙여봤다
- [ ] gRPC 또는 이벤트 기반으로 서비스 두 개를 연동해봤다

**Level 3 — 설계할 수 있어야 함**

- [ ] 주문-결제-재고-배송 흐름을 Saga로 설계하고 실패 시나리오별 보상을 그릴 수 있다
- [ ] 모놀리식을 점진적으로 분리하는 로드맵을 제시할 수 있다
- [ ] 특정 서비스 장애 시 나머지가 어떻게 동작할지(폴백 포함) 설명할 수 있다
- [ ] 이벤트 스키마 버저닝 전략을 세울 수 있다
