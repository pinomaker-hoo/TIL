# 기술 면접 (Tech Interview)

## 개요

기술 면접에서 자주 나오는 주제를 정리한다. 단순 암기용 Q&A가 아니라 **"왜 그런가"를 설명할 수 있는 수준**을 목표로, 예상 질문 / 핵심 답변 / 꼬리 질문 / 공부할 것을 함께 정리한다.

## 면접 답변의 기본 구조

기술 면접은 지식의 양보다 **설명의 구조**로 평가가 갈린다. 아래 4단계로 답하는 연습을 한다.

```
1. 정의    : "무엇인가"를 한 문장으로 정의한다.
2. 원리    : "왜 그렇게 동작하는가"를 내부 구조로 설명한다.
3. 트레이드오프 : "언제 쓰고 언제 안 쓰는가"를 비교한다.
4. 경험    : "내가 어디에 어떻게 적용했는가"를 붙인다.
```

예시 — "인덱스가 뭔가요?"

> (정의) 인덱스는 테이블의 특정 컬럼을 정렬된 자료구조로 별도 관리해 조회 속도를 높이는 객체입니다.
> (원리) MySQL InnoDB는 B+Tree를 사용해서 루트 → 브랜치 → 리프 순으로 탐색하기 때문에 풀스캔의 O(N)이 O(log N)이 됩니다.
> (트레이드오프) 대신 INSERT/UPDATE/DELETE 시 인덱스도 갱신해야 해서 쓰기 비용과 저장 공간이 늘어납니다. 그래서 카디널리티가 낮은 컬럼에는 걸지 않습니다.
> (경험) 실제로 조회 API가 느려서 실행 계획을 봤더니 `type: ALL`이 떠서, WHERE + ORDER BY 순서에 맞춰 복합 인덱스를 걸어 커버링 인덱스로 만들었고 응답이 2초 → 80ms로 줄었습니다.

## 답변 시 지켜야 할 것

| 하면 좋은 것 | 하면 안 되는 것 |
| --- | --- |
| 모르면 "정확히는 모릅니다"라고 말한 뒤 아는 범위까지 설명 | 아는 척하며 추측을 사실처럼 말하기 |
| 수치로 말하기 (2초 → 80ms, RPS 300) | "빨라졌습니다", "많이 개선했습니다" |
| 트레이드오프를 먼저 말하기 | 특정 기술을 무조건 좋다고 말하기 |
| 내가 내린 **결정과 그 이유** 말하기 | 팀이 한 일을 내가 한 것처럼 말하기 |
| 용어를 정확히 쓰기 (격리 수준 ≠ 락) | 용어를 뭉뚱그리기 |

## 거의 무조건 나오는 마무리 질문

- 최근에 해결한 가장 어려운 기술적 문제는 무엇인가?
- 장애를 낸 경험과 그때 대응 과정은?
- 성능 개선 경험이 있는가? 무엇을 어떻게 측정했는가?
- 코드 리뷰에서 주로 무엇을 보는가?
- 지금 프로젝트를 다시 설계한다면 무엇을 바꾸겠는가?

> 이 질문들은 **STAR (Situation - Task - Action - Result)** 형식으로 미리 3~4개를 문장으로 써두고 외운다. 즉석에서 만들면 반드시 두서없어진다.
