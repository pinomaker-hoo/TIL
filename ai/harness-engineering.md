# 하네스 엔지니어링 (Harness Engineering)

## 개요

하네스 엔지니어링은 AI 에이전트가 실제 환경에서 **안전하고 일관되게 목표를 수행하도록 주변 실행 시스템을 설계하고 개선하는 일**이다.

여기서 하네스(Harness)는 원래 장비를 연결하고 제어하는 장치를 뜻한다. AI에서는 모델을 도구, 데이터, 실행 환경, 평가, 권한, 피드백 루프와 연결하는 소프트웨어 계층을 가리킨다.

> 모델이 엔진이라면 하네스는 조향 장치, 계기판, 안전벨트, 도로 규칙을 포함한 자동차 시스템에 가깝다.

<br />

---

## 1. 왜 필요한가

같은 모델에 같은 목표를 주더라도 주변 환경에 따라 결과가 크게 달라진다.

```text
목표: "로그인 오류를 수정해줘"

하네스가 부족한 경우
→ 관련 파일을 못 찾음
→ 테스트 방법을 모름
→ 수정 후 검증하지 않음
→ 위험한 명령을 그대로 실행할 수 있음

하네스가 잘 갖춰진 경우
→ 저장소 구조와 규칙을 탐색
→ 로그와 테스트로 오류 재현
→ 격리된 환경에서 코드 수정
→ 린트·테스트·보안 검사를 통과할 때까지 반복
→ 변경 내용과 근거를 기록
```

모델 자체를 바꾸지 않아도 하네스를 개선하면 성공률과 재현성을 높일 수 있다. 실패했을 때 "프롬프트를 더 세게 써 보자"가 아니라 **어떤 정보, 도구, 검증, 피드백이 부족했는가**를 찾는 것이 핵심이다.

<br />

## 2. 하네스의 구성 요소

| 영역 | 역할 | 예시 |
| --- | --- | --- |
| 컨텍스트 관리 | 현재 작업에 필요한 정보 제공 | 저장소 안내 문서, 검색, 기록 요약 |
| 도구 인터페이스 | 에이전트가 환경을 읽고 변경 | 파일, 셸, 브라우저, DB, API |
| 실행 제어 | 에이전트 루프와 상태 관리 | 종료 조건, 재시도, 체크포인트 |
| 안전과 권한 | 행동 범위 제한 | 샌드박스, 최소 권한, 사용자 승인 |
| 피드백 | 행동 결과를 즉시 알려줌 | 컴파일 오류, 린트, 단위 테스트 |
| 평가 | 결과가 목표를 만족하는지 측정 | 회귀 테스트, 평가셋, 채점기 |
| 관찰성 | 문제의 원인을 추적 | 로그, 메트릭, 트레이스, 비용 |
| 지식 구조 | 에이전트가 시스템을 탐색하게 도움 | 아키텍처 문서, 실행 계획, 결정 기록 |

<br />

## 3. 프롬프트·컨텍스트 엔지니어링과의 차이

| 분야 | 핵심 질문 | 주요 대상 |
| --- | --- | --- |
| 프롬프트 엔지니어링 | 지시를 어떻게 표현할까? | 지시문의 문장과 구조 |
| 컨텍스트 엔지니어링 | 지금 무엇을 보여줄까? | 지시, 기록, 문서, 도구 결과 |
| 하네스 엔지니어링 | 어떻게 일하고 검증하게 할까? | 도구, 실행 환경, 권한, 루프, 평가 |

세 분야는 경쟁 관계가 아니라 포함·협력 관계에 가깝다. 컨텍스트 관리는 하네스의 중요한 일부이며, 좋은 프롬프트도 하네스 안에서 사용된다.

```text
AI 애플리케이션
└── 에이전트 하네스
    ├── 프롬프트와 컨텍스트 관리
    ├── 에이전트 실행 루프
    ├── 도구와 실행 환경
    ├── 권한과 안전장치
    └── 테스트·평가·관찰성
        └── LLM이 매 단계의 판단을 수행
```

<br />

## 4. 코딩 에이전트로 보는 실제 예시

### (1) 탐색 가능한 저장소

짧은 진입 문서는 모든 규칙을 담는 백과사전보다 **어디에서 무엇을 찾을 수 있는지 알려주는 지도** 역할을 해야 한다. 상세한 아키텍처, 제품 요구사항, 실행 계획은 별도 문서로 두고 필요한 순간에 읽게 한다.

### (2) 기계적으로 검증되는 규칙

"좋은 코드를 작성하라"보다 다음 장치가 더 명확한 피드백을 준다.

- 포매터와 린터
- 타입 검사
- 단위·통합·E2E 테스트
- 아키텍처 의존성 검사
- 보안 및 비밀정보 검사

에이전트가 오류 메시지를 읽고 스스로 수정할 수 있도록 오류에는 원인과 해결 방향을 담는 것이 좋다.

### (3) 읽을 수 있는 실행 환경

코드만 보여주는 것으로는 UI나 운영 장애를 충분히 판단하기 어렵다. 브라우저 상태, 스크린샷, 로그, 메트릭, 트레이스를 에이전트가 직접 조회할 수 있게 하면 문제를 재현하고 수정 결과까지 검증할 수 있다.

### (4) 장기 작업의 상태 보존

여러 컨텍스트 윈도우에 걸친 작업은 계획, 완료 항목, 실패한 시도, 다음 행동을 파일이나 체크포인트에 기록한다. 새 세션이 이전 세션의 메모리에 의존하지 않고 작업을 이어받을 수 있어야 한다.

<br />

## 5. 피드백 루프 설계

좋은 하네스는 에이전트가 결과를 관찰하고 수정할 수 있는 짧은 피드백 루프를 제공한다.

```text
목표 정의
   ↓
행동 계획 → 도구 실행 → 결과 관찰
   ↑                       ↓
   └──── 실패 원인 반영 ← 검증
                           ↓
                     성공 기준 충족
```

중요한 점은 "작업을 수행했다"가 아니라 **검증 가능한 성공 기준을 만족했다**를 종료 조건으로 삼는 것이다.

예:

- 나쁜 기준: "성능을 개선해라"
- 좋은 기준: "네 개 핵심 요청의 p95 응답 시간을 800ms 아래로 만들고 회귀 테스트를 통과하라"

<br />

## 6. 하네스 엔지니어의 주요 업무

- 에이전트가 사용할 도구와 명확한 입출력 스키마 설계
- 문서·코드·운영 데이터를 에이전트가 탐색할 수 있게 구조화
- 격리 환경과 최소 권한, 승인 절차 설계
- 테스트와 평가셋으로 성공 기준 자동화
- 긴 작업을 위한 계획, 체크포인트, 인수인계 방식 마련
- 로그와 트레이스로 실패 지점을 분석
- 실제 실패 사례를 규칙, 도구, 테스트로 환류

이는 새로운 직함 하나만을 뜻하기보다, AI 에이전트를 제품과 개발 과정에 도입할 때 필요한 **시스템 엔지니어링 관점**에 가깝다.

<br />

## 7. 흔한 실수

### 거대한 지시 파일 하나에 모든 규칙 넣기

컨텍스트를 차지하고 빠르게 낡는다. 작은 안내 문서에서 상세 문서로 연결하는 점진적 공개(Progressive Disclosure)가 낫다.

### 도구를 많이 주면 강해진다고 생각하기

비슷한 도구가 많으면 선택 오류와 보안 범위가 커진다. 책임이 겹치지 않는 최소한의 도구부터 제공한다.

### 최종 결과만 평가하기

우연히 성공한 실행을 구분하기 어렵다. 도구 선택, 중간 상태, 비용, 안전 위반도 함께 관찰한다.

### 모델이 알아서 기억할 것이라 기대하기

컨텍스트가 잘리거나 새 세션이 시작되면 작업 상태가 사라질 수 있다. 중요한 상태는 외부에 명시적으로 기록한다.

<br />

## 8. 한 줄 정리

```text
좋은 모델 + 좋은 프롬프트만으로는 부족하다.
에이전트가 보고, 행동하고, 검증하고, 실패에서 회복할 수 있는 환경을 함께 설계해야 한다.
```

하네스 엔지니어링은 모델의 지능을 직접 높이는 일이 아니라, 그 지능이 실제 작업에서 **반복 가능하고 안전한 성과**로 이어지게 만드는 일이다.
