# AI 에이전트 (AI Agent)

## 개요

AI 에이전트는 사용자가 준 목표를 달성하기 위해 LLM이 상황을 판단하고, 필요한 도구를 선택하며, 실행 결과를 바탕으로 다음 행동을 결정하는 시스템이다.

> 챗봇이 주로 "무엇을 답할까?"를 고민한다면, 에이전트는 "목표를 위해 다음에 무엇을 할까?"를 고민한다.

<br />

---

## 1. 일반 LLM 호출과 무엇이 다른가

```text
[일반 LLM]
질문 → 모델 → 답변

[AI 에이전트]
목표 → 모델이 판단 → 도구 실행 → 결과 관찰
                         ↑          ↓
                         └─ 다음 행동 결정 ─┘
                                  ↓
                             완료 여부 판단
```

일반 LLM 호출은 보통 한 번의 입력과 출력으로 끝난다. 에이전트는 목표가 끝날 때까지 **판단 → 행동 → 관찰** 과정을 반복한다.

<br />

## 2. 핵심 구성 요소

| 요소 | 역할 | 예시 |
| --- | --- | --- |
| 모델 | 상황을 추론하고 다음 행동을 결정 | GPT, Claude, Gemini |
| 지시와 목표 | 해야 할 일과 제약을 정의 | "오류를 고치고 테스트하라" |
| 도구 | 외부 세계를 읽거나 변경 | 웹 검색, DB 조회, 셸, 이메일 API |
| 상태와 메모리 | 진행 상황과 과거 결과를 보존 | 대화 기록, 체크포인트, 작업 문서 |
| 실행 루프 | 판단과 도구 호출을 반복 | 최대 횟수, 종료 조건, 재시도 |
| 가드레일 | 위험한 행동을 제한 | 권한, 승인, 샌드박스, 입력 검증 |
| 평가와 관찰성 | 성공 여부와 문제 원인을 확인 | 테스트, 로그, 트레이스, 평가셋 |

<br />

## 3. 워크플로와 에이전트의 차이

두 용어는 자주 섞여 사용되지만 제어권의 위치가 다르다.

| 구분 | 워크플로(Workflow) | 에이전트(Agent) |
| --- | --- | --- |
| 실행 순서 | 코드가 미리 정함 | 모델이 동적으로 정함 |
| 예측 가능성 | 높음 | 상대적으로 낮음 |
| 유연성 | 제한적 | 높음 |
| 적합한 일 | 단계가 명확한 반복 업무 | 경로를 미리 정하기 어려운 업무 |

```text
워크플로: 문의 분류 → 정해진 DB 조회 → 답변 생성
에이전트: 장애 원인 조사 → 필요한 로그와 코드 선택 → 수정 → 테스트
```

단계가 명확하면 워크플로가 더 저렴하고 안정적이다. 에이전트는 유연성이 실제로 필요한 문제에 사용하는 것이 좋다.

<br />

## 4. 도구 호출은 어떻게 동작하는가

모델이 직접 DB나 브라우저를 조작하는 것은 아니다. 애플리케이션이 사용 가능한 도구의 이름과 입력 형식을 모델에게 알려주고, 모델이 도구 호출을 요청하면 애플리케이션이 실제 코드를 실행한다.

```text
1. 모델: getOrder(orderId="A-123")를 호출하겠다.
2. 애플리케이션: 권한과 입력값을 검사하고 함수를 실행한다.
3. 애플리케이션: 조회 결과를 컨텍스트에 추가한다.
4. 모델: 결과를 보고 환불 가능 여부를 판단한다.
```

따라서 도구의 설명, 입력 스키마, 오류 메시지가 명확할수록 에이전트가 올바른 도구를 선택하기 쉽다.

<br />

## 5. 언제 사용하면 좋은가

에이전트가 잘 맞는 작업:

- 해결 경로를 미리 고정하기 어려운 조사와 분석
- 여러 데이터 소스나 도구를 오가야 하는 작업
- 코드 수정, 테스트, 재수정처럼 피드백 반복이 필요한 작업
- 결과를 관찰한 뒤 다음 단계가 달라지는 작업

에이전트가 과한 작업:

- 단순 번역이나 요약처럼 한 번의 모델 호출로 충분한 작업
- 실행 순서와 규칙이 완전히 정해진 업무
- 아주 낮은 지연 시간과 완전한 재현성이 필요한 업무
- 오류 한 번의 비용이 큰데 승인·복구 장치를 만들 수 없는 업무

에이전트는 성능을 얻는 대신 비용, 지연 시간, 비결정성, 보안 위험이 커질 수 있다.

<br />

## 6. 안전하게 설계하는 원칙

- 읽기 도구와 쓰기 도구의 권한을 분리한다.
- 결제, 배포, 삭제처럼 영향이 큰 행동은 사람의 승인을 받는다.
- 최소 권한 원칙을 적용하고 실행 환경을 격리한다.
- 반복 횟수, 시간, 토큰, 비용에 상한을 둔다.
- 도구 입력과 결과를 신뢰하지 말고 검증한다.
- 모든 행동과 결과를 로그로 남긴다.
- 최종 답변뿐 아니라 도구 선택과 작업 완료 여부도 평가한다.

<br />

## 7. 에이전트를 감싸는 하네스

모델과 도구만 연결했다고 신뢰할 수 있는 에이전트가 완성되지는 않는다. 컨텍스트를 조립하고, 권한을 통제하고, 실패 시 재시도하고, 테스트로 결과를 검증하는 실행 환경이 필요하다. 이 계층을 **에이전트 하네스(Agent Harness)** 라고 부른다.

자세한 내용은 [하네스 엔지니어링 문서](./harness-engineering.md)에서 다룬다.
